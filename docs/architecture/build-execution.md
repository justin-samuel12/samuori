# Build Execution

Status: **Design, accepted as direction (ADR 0028, OD-13).** It describes how a BuildSpec becomes an executed build: methods, static
Dockerfile analysis, admission and execution. Lifecycle states: [`build-lifecycle.md`](build-lifecycle.md).
Secrets: [`secrets.md`](secrets.md). Registries: [`registry-auth.md`](registry-auth.md). Isolation: ADRs 0013 and
0027.

## Build methods

| Method | For | Build definition | What the user edits |
|---|---|---|---|
| `recipe` | Developers without container knowledge | Dockerfile generated by Samuori from an approved, versioned recipe; shown read-only | Form questions (ADR 0005 as amended) |
| `dockerfile` | Experienced developers and existing projects | The user's Dockerfile in the source snapshot, unchanged | Intent fields in Samuori (context, target, args, secrets, platforms, validation, outputs); instructions in their own Dockerfile |
| `railpack` | Projects Railpack recognises, when an administrator enabled it (ADR 0047) | The plan `railpack prepare` writes on the worker, validated and pinned by Samuori; stored as lineage | Context, optional build and start commands, secrets, platform, validation, outputs; or the project's own `railpack.json` |
| `buildpacks` | Not implemented yet; the wizard shows it disabled | — | — |

Discovery suggests `dockerfile` when it finds Dockerfiles. The user chooses which one, or chooses a recipe instead.
Discovery never runs Railpack (`discovery.md`, TM-16); the wizard's *Automatic* choice recommends a method from the
static detectors and the method policy only.

## Static Dockerfile analysis

Runs in the discovery sandbox (ADR 0024): no network, no process execution, no frontend image pulls. It uses
BuildKit's Dockerfile parser and instruction packages as a library.

| Extracted | Used for |
|---|---|
| `# syntax=` directive | Frontend policy: only admin-approved, digest-pinned frontends are accepted |
| Stages (`FROM … AS name`), final and target stages | Target selection; platform hints |
| Base image references | Approved-source check; mirror routing; digest pinning suggestions |
| `ARG` names and defaults | Build-argument UI; warnings for secret-looking names |
| `RUN --mount=type=secret` (`id`, `target`, `required`, `env`) | Secrets panel and admission (ADR 0029) |
| `RUN --mount=type=cache`, `type=bind` | Cache trust-domain scoping; context checks |
| `RUN --mount=type=ssh`, remote `ADD` URLs | Refused, with an explanation (not yet designed) |
| `COPY`/`ADD` sources and `--from` | Named-context requirements; stage graph |
| Heredocs | Parsed natively; shown for review |

Anything not statically determinable is **ambiguous** and needs explicit user confirmation, never a guess. Examples:
an `id=$VAR` secret ID, a base image built from an `ARG`, or a stage chosen by variable.

## Admission (before scheduling)

1. Schema and semantic validation of the spec.
2. Static analysis results reconciled with the spec: secrets, target stage, contexts, args.
3. Frontend, base-image source, mount type and egress-preset policy checks. With `pinTags`, `FROM` tags are resolved
   to digests here (ADR 0049); an unresolvable tag blocks the build.
4. Secret binding resolution and usage policy (ADR 0029).
5. Platform, engine and isolation-profile compatibility: incompatible combinations fail here with an actionable
   message.
6. Build plan resolved, digested and stored (`buildspec.md`), with the base-image pins.

### Build readiness

The admission dry run (**Check if it can build**) and real admission also return `readiness`, a list of predicted
problems, most severe first (ADR 0050). Admission sends the build context's paths and manifest, lockfile and
Dockerfile contents to the discovery sandbox (at most 16 MiB of content and 50 000 paths), which predicts network
needs statically (`discovery.md#build-readiness`). Admission then compares them with the allowlist the method would
get: the Dockerfile presets for Dockerfile builds, the recipe's presets, or the provider's presets for Railpack and
Buildpacks, plus the policy's additional destinations and the project's egress allowances for the method (ADR 0052).
An egress item lists in `requestable` the preset or public destinations a project member may request for the
project alone (`egress.md#project-allowances`). Each gap carries the administrator advice of
`egress.md#denied-destinations`, and the developer fix when the catalog has one (for example "upgrade sharp to
0.33"). It also reports a spec port the Dockerfile does not `EXPOSE`, and repeats secrets that are undeclared or not
ready as `blocking` items.

Readiness is advice: it never changes `admissible`, and nothing new blocks a build. If the sandbox cannot run for a
recipe, Railpack or Buildpacks build, admission adds the warning `readiness-unavailable` and continues; for a
Dockerfile build an analysis failure already blocks. The policy impact preview does not predict readiness.

### Pinned base images

For each pin in `dockerfile.baseImagePins`, the worker sets the Dockerfile frontend option
`context:<name>=docker-image://<repository>@sha256:<digest>`, so BuildKit builds the pinned image wherever the
Dockerfile names the tag; the Dockerfile itself is untouched. `<name>` is the key BuildKit v0.34.0 looks up for a
`FROM` (`dockerui.Client.NamedContext`): the familiar form of the normalized reference, without `:latest`
(`node:18-alpine`, `bitnami/redis:7`, `ghcr.io/example/tool:1.2`, `node`). Only BuildKit workers receive pinned
plans (eligibility reason `engine-cannot-pin-base-images`); a Buildah worker refuses one. Pinned images still come
through the mirror and egress rules like any base image.

## Execution

1. The worker leases the attempt and prepares an isolated environment through its `IsolationProvider` (ADR 0027).
2. `buildkitd` runs inside the environment with strict egress (ADR 0025). Base images come through the mirror with
   a project-scoped token (ADR 0030).
3. `samuori-worker` acts as the BuildKit client. It supplies the build context from the snapshot and serves secrets on
   through the build session (ADR 0029; timing per the OD-15 spike). It passes build args and the target stage, and requests multi-platform output where the engine
   and pool support it. It applies the plan's image labels and annotations
   ([below](#image-labels-and-annotations)).
4. Outputs are committed to internal storage by digest. The worker runs the build-secret canary scan before
   discarding secret values.
5. The environment is destroyed or scrubbed on every outcome, and the result is recorded.
6. A ValidationRun follows: tests, scans, SBOM, provenance, `sensitive-content` (ADR 0031). Publication is a
   separate, controller-only step.

### Image labels and annotations

The plan's `image.labels` and `image.annotations` (`buildspec.md#image-labels-and-annotations`) reach BuildKit as
data, never through a shell. Verified in BuildKit v0.34.0's source and by a real build against a `moby/buildkit:v0.34.0`
daemon ([spike](../spikes/image-metadata.md)):

- **Labels** are Dockerfile frontend options `label:<key>=<value>` (`frontend/dockerui/config.go`). The frontend
  copies them into the final stage's image config after the Dockerfile's own `LABEL` instructions, so a plan label
  overrides a `LABEL` (or a custom recipe's `label` step) with the same key, and other labels, including inherited
  ones, stay. Gateway frontends (Railpack) do not receive them.
- **Annotations** are OCI exporter attributes. `annotation.<key>` annotates every platform's image manifest;
  `annotation-index.<key>` annotates the index and is sent only for multi-platform builds, because BuildKit refuses
  index annotations on a single-platform export (`exporter/containerimage/writer.go`). They apply to any frontend's
  result, Railpack's included.
- The OCI archive's own `index.json` descriptor also gets BuildKit's `org.opencontainers.image.created` set to the
  export time. That descriptor is part of the archive, not of the image, and does not change the manifest digest.
- Buildah passes them as `--label` and `--annotation` arguments (unit-tested; not yet exercised by a real Buildah
  build).
- Buildpacks builds export through the CNB lifecycle and apply neither; admission warns.

A plan with labels or annotations goes only to workers that negotiated worker protocol 1.6, which apply them
(`worker-protocol.md`). Tested by `TestImageMetadataAttrs` and `TestBuild` (Buildah).

## Railpack builds (ADR 0047)

Railpack runs only on a worker, inside the build's isolation, never on a controller or in discovery.

| Step | Where | What Samuori does |
|---|---|---|
| Admission | Controller | Method policy and provider scope (`build-method-not-allowed`); the approved builder and runtime images through the base-image policy; the provider's egress presets through the egress policy; placement needs a verified worker reporting the approved version (`provider-missing`) |
| Plan | Controller | `railpack` pin in the build plan: version, binary SHA-256 per architecture, frontend and builder/runtime images by digest, context, commands, `cacheKey` (the controller's cache scope for the project), secrets by logical ID with the variable each reaches steps as, time limit. Digest-addressed, no values |
| Dispatch | Controller | Only workers whose `Capabilities.Providers["railpack"]` is the approved version, in a pool the provider is allowed in for the project; otherwise the run waits until its queue deadline |
| Stage | Worker | Copies the binary into the attempt directory, checking its SHA-256 against the plan; a mismatch is refused and never run. Copies the context there, readable by the build user only |
| Plan | Worker | `railpack prepare` as the build user, in the attempt's systemd scope when cgroup limits are on, inside a RootlessKit user and mount namespace whose `/tmp/railpack` (where Railpack keeps mise) is the attempt's own directory. Network only through the build's egress proxy, read from a file in the attempt directory, never the command line. Railpack runs mise with only `PATH` set, so the worker stages the installed, checksum-pinned mise there behind a wrapper that adds the proxy; with strict egress it refuses to plan without one. The build's time limit applies |
| Check | Worker | Content decides, never the exit status: a failed `railpack-info.json`, no steps, no commands, no start command, no image base or a missing step reference fail the build. Every image must be an approved one; tags are rewritten to the approved digests. `secrets` becomes exactly the bound build secrets. Exit 75 is an infrastructure retry unless the egress log shows a denial, which is the build's failure |
| Build | Worker | BuildKit `gateway.v0` with the digest-pinned frontend, `cache-key` and `secrets-hash` (from binding versions, not values) as frontend options. Secrets are served through the session by variable name, mapped to logical IDs. The proxy reaches steps as BuildKit secrets, because Railpack copies step variables into the image configuration |
| Non-root user | Worker | Unless the provider's `runAsRoot` is set, the plan carries `user: 10001:10001` and the worker rewrites the exported archive: every image whose configuration runs as root gets one final layer of directory entries only, the working directory and every directory below it in the merged filesystem (whiteouts applied), owned by 10001:10001 with owner `rwx` added, and `User` set to `10001:10001` with a history entry. Files keep their owner, so the application can create files (caches, uploads, `tmp/`) but cannot change what it shipped with. Images that already name a non-root user are left unchanged. An archive with attestation manifests, or layers other than tar or gzip, is refused and the build fails as unsupported with the `runAsRoot` hint (ADR 0047, SEC-RPK-08) |
| Lineage | Worker → controller | The plan as built and `railpack-info.json` are stored as `railpack-plan` and `railpack-info` artifacts; a build whose lineage upload fails does not succeed. `GET /builds/{id}/railpack`, shown on the build page |

The OCI archive then goes through the same canary scan, runtime test, validation, SBOM, signing and publication as
every other method. Evidence: [`../spikes/railpack-builds.md`](../spikes/railpack-builds.md).

Limits: `vm-per-job` guest images do not carry Railpack yet, so Railpack builds of uploaded source run on
`rootless-dedicated-vm` pools; Buildah workers cannot run the gateway frontend; one platform per build; build
arguments are refused because the frontend ignores them; the non-root user layer covers only directories under the
image's working directory, so an application that writes elsewhere, or rewrites a file it ships, needs `runAsRoot`; mise runtimes are downloaded per build (no staged cache yet); the Railpack images
come from ghcr.io, so strict-egress workers need a ghcr.io mirror (`install.sh --railpack` runs one).

Kubernetes conversion runs reuse steps 1 and 5 with a different job: one `--network=none` step that runs an approved
tool over the input and exports its files (`kubernetes-conversion.md#execution`).

## Buildpacks builds (ADR 0047)

The CNB lifecycle runs only on a worker, inside the build's isolation, as a BuildKit build; never on a controller or
in discovery. `pack` is not used and the worker installs nothing: the lifecycle comes with the approved builder.

| Step | Where | What Samuori does |
|---|---|---|
| Admission | Controller | Method policy and provider scope (`build-method-not-allowed`); the approved builder and run image through the base-image and image-source policies; the provider's egress presets through the egress policy; placement needs a verified worker reporting buildpacks (`provider-missing`) |
| Plan | Controller | `buildpacks` pin: builder and run image by digest, CNB platform API (0.14), approved lifecycle version, context, non-secret `env`, bindings (name, type, key, logical secret ID) for bound secrets only, time limit (default 1800 s). Digest-addressed, no values |
| Dispatch | Controller | Only workers whose `Capabilities.Providers["buildpacks"]` is the platform API, which every BuildKit `rootless-host` and `rootless-dedicated-vm` worker reports, in a pool the provider is allowed in for the project |
| Run image | Worker | A first solve in the attempt's daemon pulls `FROM <run image>@sha256:…` through the daemon's mirrors and exports it as an OCI archive, unpacked as a layout (layout file names only). In layout mode the lifecycle reads its run image from disk |
| Lifecycle | Worker | A second solve of an internal Dockerfile: `FROM <builder>`, the platform directory (`env/BP_*` files, `bindings/<name>/type`) and the run image layout as local named contexts, the context copied to `/workspace`, `USER ${CNB_USER_ID}` with a non-root check, then one `RUN /cnb/lifecycle/creator -layout` with `CNB_PLATFORM_API` and `CNB_EXPERIMENTAL_MODE=warn` (layout export is experimental in lifecycle 0.21). Secrets are BuildKit secret mounts at `/platform/bindings/<name>/<key>` on that step only. The proxy reaches it as BuildKit's proxy arguments. The final `scratch` stage holds the exported layout, `report.toml` and the SBOM files, written with the local exporter |
| Result | Worker | The layout becomes the image archive only if it holds exactly one OCI manifest and every blob matches its digest. No BuildKit cache is imported or exported and the lifecycle gets no cache directory (`build-cache.md`) |
| Lineage | Worker → controller | `buildpacks-metadata` (pins, image user and entrypoint, `io.buildpacks.build.metadata` with buildpacks and processes, lifecycle and project metadata, the lifecycle report) and `buildpacks-sbom` (tar of the lifecycle's CycloneDX, SPDX and Syft files). A build whose lineage upload fails does not succeed. `GET /builds/{id}/buildpacks`, `GET /builds/{id}/buildpacks/sbom?attempt=N`, shown on the build page |

The archive then goes through the same canary scan (which also looks for the egress-proxy credential), runtime
test, validation, SBOM, signing and publication as every other method. Images run as the run image's CNB user.
Evidence: [`../spikes/buildpacks-builds.md`](../spikes/buildpacks-builds.md).

Limits: `vm-per-job` workers do not run the method yet; Buildah workers refuse it; one platform per build, which must
be the worker's; build arguments are refused (use `env`); no cache across builds; the lifecycle records the run image
by the builder's tag, so the approved digest is kept in the plan and the metadata record.

## Implementation status (WP14)

- `internal/engine/render` renders recipe Dockerfiles through one declarative renderer, `internal/recipedef`, for
  built-in and custom recipes alike ([recipe rendering](#recipe-rendering)). Commands become JSON exec-form
  instructions (shell strings run as `["/bin/sh","-c", …]` inside the build container, never on the host). Images
  must be digest-pinned, the runtime user is UID 10001, and secret mounts reference logical IDs and validated targets
  only.
- `internal/adapters/build/buildkit` is the BuildKit client (Go client library); spec text reaches the Dockerfile
  frontend only as attribute values. Each `Daemon` is
  started for exactly one build under `rootlesskit` (`slirp4netns`, `--disable-host-loopback`) with private state. Its
  sockets live in a short temporary directory because Unix socket paths are limited in length. `Stop` kills the
  process group and deletes all state, using the user namespace to remove files owned by subordinate UIDs. Output is an
  OCI archive written with mode 0600; the artifact digest is the archive's SHA-256. Build history is disabled in every
  daemon so raw step output is not retained.
- `internal/adapters/isolation/rootlesshost` is the `rootless-host` provider: trusted workloads only (eligibility never
  sends uploaded source to it). It serves build secrets through the session (`secrets.md`) and refuses Dockerfile
  contexts or paths outside the source. `samuori-worker --isolation-provider rootless-host --provider-dir …` selects it.
- Evidence (history; the target was removed with the tests, ADR 0039): `make test-buildkit` ran real builds in the Linux dev VM (BuildKit v0.34.0, RootlessKit v3.3.0, installed
  by `deploy/dev/lima/provision-buildkit.sh`). It covered a recipe build, application failure, the wall-clock limit and
  daemon separation with cleanup.
- After a successful build the provider runs the build-secret canary and the runtime test (`validation.md`), and
  the worker uploads the masked run log as a `log` artifact before its final report.
- **Pending:** `vm-per-job` execution, its VM-boundary limits and every acceptance test that needs a KVM host
  (OD-12b). Disk limits for daemon state. No CI host yet.

## `rootless-dedicated-vm` provider (WP13)

The same provider package also serves `rootless-dedicated-vm` (ADR 0027): a Linux VM dedicated to Samuori and to one
trust domain, which may be the worker host itself. `samuori-worker --isolation-provider rootless-dedicated-vm` refuses
to start unless every condition holds:

| Condition | Setting |
|---|---|
| The host is a virtual machine (`systemd-detect-virt --vm`) | — |
| The operator confirms the VM runs nothing but this worker | `--dedicated-host=true` |
| Strict egress: build user, worker firewall, egress proxy and mirrors (`egress.md`) | `--egress strict` (default), `--build-user`, `--egress-listen`, `--mirrors` |
| Per-daemon memory and process limits through systemd | `--cgroup-limits systemd`, `--max-processes` (default 2048) |

Each environment's daemon runs in its own systemd user scope of the build user (`Delegate=yes`, `MemoryMax` from
the build's memory limit, `MemorySwapMax=0`, `TasksMax`). The daemon moves into a child cgroup of that scope before
it starts, so runc creates every step's cgroup inside the scope and the limits cover the daemon and all its steps.
A kill by the memory limit is reported as a resource-limit failure (`memory.events` `oom_kill`, or the scope's
`oom-kill` result). The build user needs lingering enabled (`loginctl enable-linger`) so its systemd user manager
runs without a login session.

The provider stops accepting builds after `--recycle-after-builds` (default 100) or `--recycle-after-hours`
(default 24) by reporting no free slots. Replacing the VM is the operator's job; Samuori does not manage these VMs.

### Worker self-test (OD-22)

Every worker is verified on its own. `POST /workers/{workerId}/self-tests` tests one worker; `POST
/worker-pools/{poolId}/self-tests` starts one test per connected worker of the pool that offers its profile with
strict egress. The controller also starts tests by itself: when a worker of an approved pool connects, when a pool is
approved, and every 30 minutes for workers whose newest test is missing, older than 20 hours, or for another profile
or configuration. A failed test of the current configuration waits for an operator to rerun it.

The worker runs a test only while idle and advertises no free slots until it ends. Checks run through the provider's
real configuration, each build in a fresh environment:

| Check | How |
|---|---|
| SEC-ISO-01, 02, 03, 05, SEC-NET-01, SEC-ISO-04 | A probe build reads its UID map, seccomp mode, capabilities, devices and mounts, looks for engine sockets, tries direct internet, DNS and the metadata address, and connects to the telemetry socket |
| SEC-ISO-07 | A second environment for one attempt is refused, and two attempts get two daemons |
| SEC-ISO-08, SEC-DOS-02 | A build allocating past its 1 GiB limit must end as a resource-limit failure |
| SEC-DOS-03 | A build spawning more processes than `--max-processes` must hit `EAGAIN` |

**Configuration digest.** Each worker reports a digest of what a test depends on: worker version, provider, OS and
architecture, engines, profiles, strict egress, and the provider's own digest (build user and group, proxy address,
mirrors, cgroup limits, process limit, recycling, daemon directory, and the content hashes of RootlessKit, buildkitd
and the probe binary). A test records the pool profile and the digest it ran against. The controller accepts a report
only from the worker the test was sent to, only while it runs, and records `passed` only when every check in
`isolation.SelfTestChecks` passed and the digest did not change during the test; missing or errored checks fail it. A
test that has not reported within 45 minutes counts as failed.

A worker is eligible for uploaded source while its pool is approved and its newest finished test passed less than 24
hours ago, for the pool's profile and the worker's current digest. The Workers page shows each worker's result (marked
outdated after a change) with **Run self-test**, and each pool's verified workers.

Evidence: `TestDedicatedVMSelfTest` (all 10 checks pass in the Linux dev VM, a Lima VM on Apple Virtualization
with systemd 255 and cgroup v2) and `TestDedicatedVMRefusesWeakSetups` in `make test-buildkit`;
`TestPoolSelfTest` and `TestStaleSelfTestTimesOut` cover the protocol, authorization, busy workers and failure
recording.

## Engines (D05)

The `rootless-host` and `rootless-dedicated-vm` provider runs one of two engines, chosen per worker with
`--engine` (`buildkit` by default, or `buildah`). The engine is part of the worker's configuration digest, so
changing it invalidates the self-test. Workers advertise their engine, and the Workers & pools page shows it.
Both engines implement `engine.Runner` (`internal/engine`), so the same provider code, egress rules, limits, canary,
runtime test and self-test apply.

| | BuildKit (`internal/adapters/build/buildkit`) | Buildah (`internal/adapters/build/buildah`) |
|---|---|---|
| Process | One rootless `buildkitd` under RootlessKit per build | One `buildah build` process per build, no daemon |
| State | Private daemon root, removed afterwards | Private storage and run roots, removed afterwards inside the build user's user namespace |
| Source | Streamed from the worker through the session | A copy staged in the build's group-shared directory; the worker's files keep their permissions |
| Proxy for RUN steps | Predefined proxy build arguments | Proxy environment (`--http-proxy`); mirrors in `NO_PROXY`; neither enters image history |
| Mirrors | `buildkitd.toml` | Per-build `registries.conf`, short names disabled |
| Limits | The daemon in a child cgroup of a systemd user scope | Buildah in a child cgroup of a systemd user scope; the scope's memory events are recorded at exit, because the scope ends with Buildah |
| Secrets | Released just in time through the session (ADR 0029) | **None.** Secret-bearing builds are refused and never scheduled on Buildah workers (OD-26) |
| Private base images through the authorizing mirror | Build-scoped tokens through the session | Not yet: pulls are anonymous, so the mirror refuses private images (fails closed, OD-26) |
| Base images pinned at admission (ADR 0049) | Named contexts `docker-image://repository@sha256:…` | **None.** Pinned plans are never scheduled on Buildah workers (`engine-cannot-pin-base-images`) and a Buildah worker refuses one |
| Image labels and annotations | `label:` frontend options and `annotation.` exporter attributes | `--label` and `--annotation` arguments |

Scheduling and admission enforce the secrets rule: a worker whose engines deliver no secrets is not eligible for a
secret-bearing build (`engine-cannot-deliver-secrets`). Admission warns when the only verified workers that could
build a secret-bearing spec run Buildah. A worker needs `buildah`, `runc` and `netavark`; the GPL `crun` is not
needed. Ubuntu's packages ship AppArmor profiles that let them create user namespaces. Evidence:
[buildah-isolation](../spikes/buildah-isolation.md); the full self-test and the runtime tests pass with Buildah in
the dev VM (`TestBuildahSelfTest`, `TestBuildahRuntimeTests`).

## Generated recipes

Recipes render a deterministic Dockerfile from versioned definitions and the spec's intent fields. The rendered file:
- is shown read-only;
- contains no secret values (secret mounts reference logical IDs only);
- is stored as an artifact with its digest in the plan.

### Recipe rendering

Built-in and custom recipes are both declarative definitions (stages and steps, `internal/recipedef`) rendered by
the same code (ADR 0041, ADR 0047). Built-in definitions are embedded with the catalog
(`internal/recipes/catalog/<id>-<version>.yml`); the worker looks one up by the plan's recipe ID **and** version, so
a recipe or version this release does not ship is version skew (`render.ErrNewerPlan`), as is a custom step of a
kind it does not know. Every built-in version a released controller can put in a plan stays in the catalog.

Built-in definitions may also use steps that take values from the plan, which custom recipes cannot (validation and
rendering refuse them): a stage's `runtime: build|run` image (the runtime resolved at admission),
`run: {command: install|build}` (the BuildSpec's command, skipped when unset), `start` (the start command as `CMD`)
and `exposeAppPort` (`EXPOSE` of the port for an `http-service`). A built-in final stage may be unnamed.

Built-in output keeps its established form, so existing plans render byte for byte as before (golden test
`internal/engine/render/golden_test.go`, 1,312 plans):
- the header names the recipe and says to change the BuildSpec;
- build arguments (names up to 128 characters) are declared in the first stage only;
- `COPY` and `ENV` use the plain form (`COPY . .`, `ENV NODE_ENV=production`); paths and values are validated so
  they are single tokens;
- every install or build step mounts every build secret of the plan by logical ID (an unbound optional secret as
  `required=false`); install steps reach the network through the egress proxy, build steps run with
  `--network=none`.

Custom recipes render as ADR 0041 describes: JSON-form `COPY`, quoted `ENV`, parameters and build arguments in
every stage, and only bound secrets a step lists.

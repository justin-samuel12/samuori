# 0059. Deployment files for built images

Status: **Accepted** (2026-10-28, owner request; provisional, may change during acceptance testing). Extends
[ADR 0053](0053-image-download-and-build-deletion.md); complements [ADR 0048](0048-kubernetes-artifact-generation.md);
extended to a whole project by [ADR 0061](0061-deployment-files-for-a-project.md).

## Context
Next to "Download image", the owner asked for "a docker compose and/or helm file referencing the image AND if it's
pushed to a registry, make it point to that with tag/sha". ADR 0048 already converts images and sources into
Kubernetes manifests, but as a worker job with an approved provider, review and revisions. People who only want to
try an image need a small, immediate starting file.

## Options
- **Generated by the controller from Samuori's own records (chosen):** no worker, no provider, no untrusted input; the
  files are deterministic and contain only what the BuildSpec and the publication record state.
- **A Kompose or Move2Kube conversion (ADR 0048) for every image (rejected):** needs an approved provider and a worker,
  and is too heavy for a quick start; it stays the way to get reviewed, validated manifests.
- **Templates the user fills in by hand (rejected):** the image reference with tag and digest is what people get wrong.

## Decision
- **Scope.** Samuori writes starting files; it does not deploy, apply, reconcile or orchestrate anything
  (`../product/vision-and-scope.md`). The files say so in their header.
- **API.** `GET /artifacts/{id}/deploy` returns the reference the files use and the image's publications;
  `GET /artifacts/{id}/deploy/compose` returns `compose.yml` and `GET /artifacts/{id}/deploy/helm` a Helm chart
  `<app>-<chart version>.tgz`. Each takes an optional `publicationId`. Anyone who may see the image may use them
  (developer, maintainer, publisher, security reviewer, administrator, with project visibility), as anyone who may see
  an image already sees its publications' locations. File downloads are audited as `image.deployment_files`.
- **Image reference.** With a successful, unretired publication: `<registry>/<repository>:<tag>@<digest>` from the
  publication's recorded location and manifest digest, the tag being its first requested tag or else its
  `samuori-<digest>` tag. The newest publication is the default; a `publicationId` that is not such a publication of
  the image is refused. Without one: the name `docker load` gives the downloaded image (ADR 0053), with `pull_policy:
  never` in Compose and `pullPolicy: Never` in Helm, so no node pulls a different image of the same name from a public
  registry, and a note that the image must be loaded first. Samuori never invents a registry.
- **Content from the BuildSpec.** `spec.application.port` becomes the container port, a published port in Compose
  and a ClusterIP Service in Helm (for a frontend and backend image, ADR 0055, that is the launcher's port);
  `healthPath` becomes Kubernetes liveness and readiness `httpGet` probes. Compose gets no healthcheck, because it runs
  inside the container and Samuori cannot assume the image has `curl` or `wget`; the file says so. Workers and
  command-line tasks get no ports, Service or probes; a command-line task becomes a Kubernetes Job. The BuildSpec
  declares no runtime environment variables, secrets or resources (its secrets are build-time only, ADR 0029), so the
  files offer empty placeholders: Compose comments for `environment` and `env_file`, Helm values `env`,
  `existingSecret` (the name of a Secret the user creates) and `resources`. No secret IDs, secret values, build
  argument values or internal storage paths are written.
- **Chart.** `Chart.yaml` (apiVersion v2, name the application slug, version the build version as semver: `2026-10-27.3`
  becomes `2026.1027.3`, anything else `0.1.0+<version>`, appVersion the build version), `values.yaml`,
  `templates/_helpers.tpl`, a Deployment or Job, a Service when the image serves, and `NOTES.txt`. Helm requires the
  names `Chart.yaml` and `values.yaml`; templates use `.yml` (`../developers/toolchain.md`).

## Consequences
- A published image's files pin the exact manifest digest, so a moved tag cannot change what runs.
- The files are only as complete as the BuildSpec: environment, secrets and resources are left to the user, and a
  conversion (ADR 0048) remains the reviewed path to production manifests.
- Reversible: three read-only endpoints and one UI dialog; no stored state.
